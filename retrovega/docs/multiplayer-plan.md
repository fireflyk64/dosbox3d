## 0. Where it stands, and the user's rulings

- **Today a room shares no flight.** Two pages in an RV- room meet in RV-LOBBY, the host's Fly boots RV.EXE on
  every page, and each plays its own campaign alone. The page says so: `web/gamefiles.js` (the `rv` entry has
  `noFlight: true`, and its help text says "flights are not shared yet"). The layer recognises RV.EXE
  (`src/cpu/wcnet_game.cpp` kGames row, `rv_params`), but its dispatcher `rv_check_hooks`
  (`src/cpu/wcnet_hooks.cpp` ~2100) only watches the thunks, logs them, times the flight, and passes the page's
  keys and stick in. Nothing crosses to the other machine. It was never tried.
- **The user's rulings (2026-11-02):**
  - "make it happen: we need the multiplayer to work in the same way" as WC1 and WC2.
  - "the design should be similar to WC1 since there are no solo missions and I think users don't have turrets".
    So: the host runs the mission, every other human flies a wingman seat, and there are no gunner or drone seats.
  - "RetroVega is actively being updated, so we need a way to map the correct functions even if they change".
    So the layer touches RV.EXE only through its fixed interface (section 3).
  - "make a plan containing all the entry points and how they would slot into the dosbox3d subsystem", then build
    it in a fresh context.
- **The standing working rules:**
  - Commit, push and full-deploy after each finished step ((memory note `commit-deploy-each-step`)).
  - Never edit the worktree while a deploy runs: it builds `/rv` and the DOS game from the working tree.
  - Work in `~/dev/rv-gx` (branch `retrovega-gx`). The main tree `~/dev/dosbox3d` is shared, fast-forward only.

## 1. How it slots into dosbox3d

```
 RV.EXE (DOS, in the emulator)                      dosbox3d (C++)                               the page
 ┌─────────────────────────────┐   watched IPs    ┌──────────────────────────────────┐  frames   ┌──────────┐
 │ RVHOOK (paragraph 0)        │ ───────────────► │ wcnet_hooks.cpp dispatcher        │ ◄───────► │ wc.js    │
 │  thunks 0x20.. (jmp far)    │                  │  build_watch_list / check_hooks   │  lobby,   │ lobby,   │
 │  sites 0x400.. (flight loop)│ ◄─ GameCall ──── │ wcnet_vm.cpp (GameCall, jobs)     │  WebRTC   │ seats,   │
 │ DGROUP fixed block 0..0x7400│ ◄─ ds:: r/w ──── │ wcnet_memory / wcnet_ds.def       │           │ Fly      │
 │  (names = WC.EXE's)         │                  │ wcnet_session.cpp (exchange,      │           └──────────┘
 │ C code, data (moves freely) │                  │  seats, start state, mission end) │
 └─────────────────────────────┘                  │ wcnet_events.cpp (fire, damage,   │
                                                   │  spawn, despawn, AI hold-offs)    │
                                                   │ wcnet_entities (EntityMap ids)    │
                                                   │ wcnet_transport / wcnet_lobby     │
                                                   └──────────────────────────────────┘
```

- **Data:** `wcnet_ds.def`'s `WC_DS(name, WC, SM2, WC2, SO1, SO2)` gets a 7th column, RV, generated by
  `retrovega/tools/rvabi.py --column`. `scripts/wcport.py` writes that file too and must learn the column.
  `load_ds` (`wcnet_game.cpp:49`) has no RV column today, so every `ds::` name reads as 0 for RV.
- **Code places:** `load_rv_code` (`wcnet_game.cpp:200`, empty now) binds `code::` names with `root()` to the
  offsets in `src/cpu/wcnet_rv.h` (`kRvThunks`, `kRvSites`). Every RV place is root-image: no overlays.
- **Dispatcher:** route `BUILD_RV` through the common `build_watch_list` (`hooks.cpp:951`) and `check_hooks_slow`
  (1441-1686) instead of the log-only `rv_check_hooks`. Keep what `rv_check_hooks` does that the common path doesn't:
  - the simulator's silence (everything between `simulatorStart` and `simulatorEnd` ignored);
  - `rvFrameDone` → `perf_frame`;
  - `uiMode` / `missionEnded` ending the measured flight;
  - the quiet log levels (`aiFighterThink` and the other per-step thunks at level 3: the page's console choked);
  - the page's keys/pointer/Esc work (`web_keys_and_buttons`, `set_pointer`, `escape_tap`).

  `rv_check_hooks` returns when CS ≠ loadSeg. The trampoline's NOP runs with CS = DS, so it must be watched too.
- **Calls into the game:** `GameCall::invoke` (`wcnet_vm.cpp:85`) writes a far-call thunk at
  `aSorryAnErrorHasOccured` and runs a trampoline NOP at `aLoadingWingCom+101`. RV reserves both:
  - DS:0x0400 `aLoadingWingCom` (128 bytes), so the NOP is at DS:0x0465;
  - DS:0x0480 `aSorryAnErrorHasOccured` (256 bytes).

  Jobs run from `mainLoopTop`, or in place of an intercepted call. RV promises that every thunk can be called from
  `mainLoopTop` with interrupts on (spec 6.5).
- **Session, transport, lobby, the page's room** are game-agnostic and stay as they are, except for the page entry
  (step 4).
- **The native `/rv` build** (retrovega/host/web: the game compiled to wasm, `hle.c` answering DOS) has no layer.
  Multiplayer is the `/dosbox` page's emulated RV.EXE only.

## 3. Keeping up with a game that keeps changing (the user's point)

- **The layer may touch RV.EXE only through the interface:**
  - the RVHOOK thunks and sites at fixed offsets: the bodies move freely, and the engine's own callers go through
    the thunks, so a hook sees every call;
  - the fixed block: `build.sh` fails the link if anything in it moves;
  - the puppet header at DS:0x10 (`"RVPUPPET"`, the ABI version, the slot counts, the record sizes), which
    `rv_params` reads.

  Never a raw RV address in `src/cpu`: no `aiSetSpeedReturn`-style jumps, no `despawn_slot_quietly` offsets.
- **One source:** `abi/rvabi.def`. `rvabi.py` generates the game's `src/rvhooks.h`, the layer's
  `src/cpu/wcnet_rv.h` (`--layer`) and the `wcnet_ds.def` column (`--column`).
- **Gaps to close first (step 0):**
  - Nothing regenerates or checks `wcnet_rv.h` or the column when `rvabi.def` changes. Make `retrovega/build.sh`
    regenerate both into a temp file and fail when the checked-in copies differ.
  - A version mismatch at load leaves multiplayer half-working: `rv_params` falls back to spec 4.6's numbers. It
    should switch the layer to the log-only path for RV with a clear log line, and the page should show "this build
    of the game and the emulator don't match" in the room.
  - Bump `ABI_VERSION` (`rvabi.py`) on any incompatible change to the block, a thunk's arguments or a site.
- **A new hook** is one `FUNC` line in `rvabi.def`, a body named `X_impl`, and a call through the thunk from the
  engine. The generated headers carry it to the layer.
- Since the page ships RV.EXE and dosbox.wasm in one deploy, a mismatch could only reach users through a broken
  build. The check above stops that before it ships.

## 4. What is different from WC1, and needs a change or a ruling

4.1 **Pacing.**
- RV steps at `LOGIC_HZ` 30 (`logic.h:9`; spec 6.1's "20 per second" is stale). Speeds still convert at
  `KPS_HZ` 20.
- The layer paces WC1 per frame at 20 by default (the page's FPS box, 800 cycles per fps; (memory note `frame-pacing`)), and
  `pace_fps` is 0 for non-WC1 games (`wcnet_perf.cpp:63`). RV caps itself (`flight.c` ~3516-3524).
- Paced at 20, RV would run at two thirds of its speed. Plan: the layer paces RV at 30 (a `GameParams` or
  `is_wc1_like()` choice), and RV skips its self-cap when `rvNetRole` ≠ 0.
- Up to 31 Locations a frame at 30 fps is more traffic than WC1's 9 at 20. Watch the low-mode window (6 frames).

4.2 **Seats.**
- In a room of two, `plan_seat_of_two` (session.cpp:1194) gives WC1 slot 1 unconditionally. RV's slot 1 is just
  the first nav-0 ship (`world.c` ~161, `logic.c` ~478). Use `wing_slots_wc1` (929) for rooms of two as well.
- In a room of three: `plan_seat` (1214) / `enqueue_server_spawn` with `Spawn.again`, `resolve_seat_spawn`,
  `park_beside`, `wing_station` (1294, 1605, 1620).
- A room of two must play exactly as before when the room-of-three code changes (the user's rule from WC1/WC2:
  `plan_seat_of_two`).
- On a client, `EntityMap::record_spawn` (`wcnet_entities.cpp:154`) swaps ids: its own net id is local slot 0,
  and the host's body is net 0.

4.3 **Mission start.**
- WC1's client is held in `pre_briefing_handshake` until it has the host's mission. RV's `missionStarting` comes
  after the mission is loaded and briefed (`game.c` ~1310), and the sprite sets load at the briefing
  (`ships_want`).
- So RV needs a meeting point BEFORE `campaign` loads the mission:
  - the `campaignNode(node, mission)` / `missionLoaded(mission)` probes, or a new `flyMission`-like thunk (WC2 has
    one: hooks.cpp:1449);
  - the client reloads `missionShipTable`/`navPointTable` from the node and mission the host sends.
- `RV.EXE /fly N` (MIS/SERIES, `game.c` ~1846-1867) starts both instances in the same mission without any
  handshake: use it for the first milestone's rig.
- **Ruling needed:** whose campaign does a client fly, and what does its own bunk save remember? WC1's client
  flies the host's mission.

4.4 **Mission end and fate.**
- WC1 shares fate: a wingman's death shows "YOU HAVE DIED" on the host. RV needs each human's own end: a client's
  own end goes as `PlayerEnd` (2660), and the server applies shared fate (1761-1786) except for WC2's landings.
- `logic_end` (`logic.c` ~3267) scores a win only if the host itself landed near nav 0. Score for any human home,
  or the host's view of it.
- `logic_wingman_lost` (`logic.c` 228) marks a dead human wingman's pilot as lost in the campaign. Later
  missions then drop that wingman's record (`campaign.c` ~262), and the seat with it. Gate it for humans.
- Status 6 (carrier lost) is not shared (section 2.3).
- The coming-home sequence (`landing_show`, Kit at the plate, `damage_home_tier`) is each player's own. On a
  client, `landedOn` arrives in `MissionEnd`, and `flight_fly` runs the landing show when status is 1 and
  `landedOn` is set.

4.5 **The autopilot.**
- `logic_autopilot` moves only CTL_AI ships of the player's side, so a human wingman is left behind.
- The engine calls neither `autoAnimation` nor `autopilotFinished`: no `AutoPilotEvent` reaches the client.
- Clients step over `autopilotKey`: only the host flies the autopilot.

4.6 **Damage, collisions, the systems: each human's own.**
- `damage.c` (19 systems, `g_sys`, the reserve past the hull, cockpit overlays, the repair system, the power
  plant's trickle) models the LOCAL player only. A human is hurt on its own machine (WC1's rule). The host
  mirrors a human's shields, armour and hull through `write_health` (`wcnet_memory.cpp:97`) but never kills a
  human; the end comes from the owner's `PlayerEnd`.
- `ram()` (logic.c), the collision caps (2026-11-02, the user's rules; docs/gameplay.md M6):
  - The player is whoever is `rvController[a] == CTL_PLAYER`.
  - **Never `a == 0`:** Watcom -ox compiled `a == 0 && ...` there as a constant 0 (section 6).
  - On the host a human wingman is CTL_PUPPET. It gets no shove (`ram_moves`) and no capital-ship stop
    (`ram_stop`), and the host's damage to it must not apply.
  - Proposal: each machine computes its own human's bump against the other ship. The enemy's share (the user: it
    takes what the human took) comes from the server, which works the human's cap out on the puppet's mirrored
    health, the way a wingman's bolt hits are reported. `ram_cap_player` takes a slot.
  - Two NPCs each take at most that shield and half that armour, so no bump ever kills an NPC ("to avoid
    tragedy"). Into a capital ship over 100 kps: stopped dead, throttle 0.
- Rocks are local hazards (`rvFlags` bit 2, `rocks.c`). A wingman reports its own rocks' hits (WC1's rule), which
  fits RV's per-player fields.
- `shot_source` makes the proxy slot 32 an ET_BOLT whose parent is the shooter (`shots.c` ~213), so
  `our_own_bolt` and the remote-bolt rule work unchanged.

4.7 **The missile lock and the dumbfire's aim.**
- `missile_target_of` and `dumbfire_aim` (the user's 15-degree help at launch, 2026-11-02) read `g_sys.target`
  for the local player and `rvTarget` for AI.
- A replayed launch on another machine must aim the same way. Carry `missileTarget[shooter]` (WC1 does,
  `capture_lock`) and read it for CTL_PUPPET shooters.
- The Schroedinger carries 2 dumbfires and a heat seeker (the user's).

4.8 **Things that are local and stay local:**
- the arrow ramp (`key_ramp`, WC1's, traced 2026-11-02);
- the VDU pages (damage, weapons G/W);
- the comm menu (orders reach only `is_wingman` ships, which needs CTL_AI, so a human is never ordered);
- music;
- the fresh-bolt streak (`Shot.fresh`: a replayed `fireGunFromShip` from `mainLoopTop` arrives with `fresh` 2 and
  is drawn at its muzzle).

The AI wingman's lines and the lost-wingman song must not fire for a human.

4.9 **The world view.** `step_scene` hides ships far from the HOST (`ET_OFFSCENE`). It should go by the nearest
human, or a client's ship would fly into a world the host has hidden.

4.10 **The page.**
- `web/gamefiles.js` `rv`: drop `noFlight` (it hides the mission, connection and collision menus) and fix the help
  text.
- RV has no mission picker: the host's campaign decides.
- The Players counter / room of one is `WCSOLO=1` ((memory note `solo-room`)), the game as it is.
- `scripts/web-smoke.sh` has the WC two-page smoke; add an RV pair.

## 5. The steps

Each step: build, both play-test suites, the rigs, commit, the full deploy (section 7). A room of two must
work at every step.

**Step 0: plumbing, no behaviour change.**
- `src/cpu`:
  - the generated RV column in `wcnet_ds.def` (and `wcport.py`);
  - `load_rv_code` binding the thunks and the sites marked "bind" in 2.1 and 2.2;

## 6. Traps this session found (they will bite again)

- **Watcom -ox miscompiles slot-0 tests.**
  - Once in the physics: an `if (s == 0) … else`.
  - On 2026-11-02 in `ram()`: `a == 0 && rvController[0] == CTL_PLAYER` became `xor cx,cx`. Even as a `?:` the
    player's arm was gone, and on DOS the player took an NPC's collision cap. The host and DOS hashes parted at
    M6.2 and M6.6.
  - Ask `rvController[s] == CTL_PLAYER` (only the local player is CTL_PLAYER). When C behaves impossibly, read
    `wdis -s=src/logic.c build/dos/logic.obj`.
  - Multiplayer adds many "is this the local player" tests: write them that way from the start.
- **Play tests:** a test's dice are its place in the table (`randomSeed = 0x52560000 + index × 977`). Add new tests
  at the END. M8.6 and M8.18 pass on their present dice only.
- **The host and DOS must hash the same** (`tests/play/playtest.sh --dos`). A difference means a 16-bit int
  somewhere, or the compiler.
- **Never edit the worktree while a deploy runs.** `/rv` once went live with uncommitted code. Prepare the next
  change as a patch script in the scratchpad and apply it after DEPLOY OK.
- **RVT.EXE adds a damage overlay every 3 s** as benchmark scenery: judge looks from RV.EXE.
- **Memory:** RV.EXE leaves 30.2 KB of conventional memory (2026-11-02). DGROUP is nearly full: new tables
  `__far`. The game has no heap: fixed `MEM_ARRAY`s only ((memory note `retrovega-fixed-memory`)). Keep RV's multiplayer
  side small; the layer (C++) has no such limit.
- **`build/dos` is 482 MB.** Per-instance rig directories should symlink every file but the written ones
  (RVLOG.TXT, *.BMP, BUNK*.SAV, RVSETUP.CFG, WALK.TXT), and copy the EXE under test.
- **The sandbox's pid limit:** one two-instance pair at a time, each with its own ports ((memory note `sandbox-pid-limit`)).
